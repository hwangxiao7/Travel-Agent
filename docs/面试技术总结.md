## 0. 30 秒电梯稿

我做了一个北美「说走就走」旅行规划产品：**iOS（SwiftUI）为主 + Web Beta（React/Vite）同构外测**，后端 **FastAPI** 跑一套 **编排型 RAG Agent**。

核心不是 Chatbot，而是：**检索与硬约束决定「去哪」，LLM 在接地上下文里写「怎么玩」，校验挡住幻觉**。刻意不用 ReAct / LangGraph——地点幻觉和车程不可靠，不能把「下一步调什么工具」交给模型自选。

## 1. 技术栈（前后端）

### 1.1 一览表（简历可直接摘）

| 层 | 技术 | 面试怎么说 |
|---|---|---|
| **iOS 主产品** | SwiftUI、async/await、URLSession、Keychain JWT、UserDefaults | 原生体验；环境 Local/Beta/Custom 可切；智能全在服务端 |
| **Web Beta** | React 19、Vite、TypeScript、手写 CSS | 与 iOS 同构双模式，同 Wi‑Fi 外测；不绑公网隧道 |
| **API** | Python 3.10+、FastAPI、Pydantic v2、Uvicorn、httpx | 异步 HTTP；契约用 Pydantic；外部地理/天气用 httpx |
| **数据** | SQLAlchemy 2 + SQLite；`.embed_cache.json` | MVP 单机可演示；用户/行程/Taste/埋点/反馈入库 |
| **LLM** | OpenAI 兼容 Chat Completions（可切 Ollama / 云厂商） | 业务只依赖 `chat.completions`；`.env` 换端不改编排 |
| **Embedding** | local `BAAI/bge-small-en-v1.5` 或 API；磁盘缓存 | 无 key 也能语义检索；小语料全量 cosine |
| **RAG** | 自研 `RAGPipeline`（非 LangChain） | 硬过滤 / 双路径 / 搜广推是一等公民 |
| **地理** | Nominatim、Overpass、OSRM | 地点真实、车程可算；best-effort 降级 |
| **可观测** | OTel、Prometheus `/metrics`、结构化日志、`trace_id` | 端到端串客户端→LLM/外部 API |

### 1.2 前端架构要点

**产品模型（不是万能聊天页）：**

| 模式 | 用户意图 | API | 后端管线 |
|---|---|---|---|
| Surprise me | 今天干嘛 | `/api/activities` → venues | 开放词表活动推荐 + 就近场馆 |
| Trip planner | 短途出行 | `/api/plan` 或 `/api/search` → `/api/select` | 闭域 RAG + 接地行程 |

**契约：** 客户端只组装请求、展示结果、带 JWT；**不做意图理解 / 检索 / grounding**。换皮（iOS↔Web）不改变规划分布。

**iOS 工程点（可展开）：**

- `APIClient` 统一 Base URL + Bearer；超时约 120s（规划管线可能数十秒）
- Keychain 存 JWT；`AssetStore` LRU（贴纸不全量进包）
- 中英切换用根视图 `.id(language)` 重建，避免「只写 UserDefaults 不刷新」
- 双击喜欢本地缓冲，批量 flush，降低 IO

**Web 工程点：**

- Vite `host: true` 局域网访问
- TypeScript + 薄 `api/client`；贴纸 / likes 与 iOS 行为对齐

### 1.3 后端架构要点

```
routers/     → HTTP 契约（plan/search/activities/account/taste/likes/beta…）
agents/      → 业务流程编排（planner / grounded / refiner）
services/    → 可替换能力（RAG / LLM / POI / geo / persona / crowd…）
knowledge/   → 闭域可规划语料 + 贴纸资源
```

**分层面试话术：**  
换 embedding / OSRM / LLM 供应商 → 动 `services`；换「先检索再接地」产品流程 → 动 `agents`。避免一个 `plan()` 大函数，也避免 MVP 拆十个微服务。

**行程语义三轴（影响打分，不是 UI 装饰）：**

- Drive band：`local` / `regional` / `distant`（车程带）
- Mode：`drive` | `fly`
- `trip_kind`：`local_play` | `away`

## 2. AI Agent：形态、流水线、为什么这样设计

### 2.1 我们建的是哪种 Agent？（必背）

| 形态 | 采用？ | 一句话 |
|---|---|---|
| **Orchestrated Pipeline Agent** | ✅ | Python 固定编排；LLM 只在定点调用 |
| ReAct / Tool-calling 循环 | ❌ | 地点/车程不能交给模型自选工具 |
| LangGraph / 多智能体 | ❌ | 强约束场景框架收益小、失败难讲 |
| 纯 Chat Agent | ❌ | 产品要可成行行程，不是闲聊 |

**核心职责分离（设计灵魂）：**

1. **检索 / 规则定 where** — 可验证、可评测、可硬过滤  
2. **LLM 写 how** — 叙事与节奏，必须 grounded  
3. **`validate_grounded_output` 挡幻觉** — 不合格回退目录骨架  

### 2.2 Planner 主循环（口述画图用）

```
intent / chips
  → understand（规则抽意图 + LLM 活动短语英文化）
  → rewrite query
  → retrieve（闭域 corpus embedding）
  → hard filter（车程 / specialty… 可行性 > 相关性）
  → score（语义 + 距离偏好 + persona + 搜/推/广）
  → 双路径：corpus 命中 | 语义不像 → Nominatim POI
  → 并行增强（天气 / OSM）‖ 摘要 LLM
  → grounded JSON + validate
```

**Surprise 是另一条轻量 Agent：**  
catalog 向量推荐 → vibe 多样化 →「附近」用地理 API 解析真实场馆（地域受限 vs 随处可玩，按距离重排）。

### 2.3 LLM 调用面为什么刻意收窄？

只暴露类似 `generate_summary` 的单次补全 + JSON 解析；**没有** streaming / function calling / 多轮 tool loop。

| 调用点 | 目的 | 失败降级 |
|---|---|---|
| 活动短语改写 | 中文「冲浪」→ 英文检索短语 | 关键词 |
| query rewrite | 合成检索句 | 规则拼装 |
| plan summary | 2–3 句人话 | 模板 |
| grounded days | 逐日 JSON | 目录 day plan |
| refine | 轻量改行程 | 规则优先 |

**好处：** 延迟可控、失败可预期、评测边界清晰。  
**代价：** 多跳推理写进 Python，不交给模型「自己想下一步」。

### 2.4 为什么不用 LangChain / 向量库 / 纯 LLM？（高频追问）

| 不做 | 原因（面试答案） |
|---|---|
| LangChain 全家桶 | 车程硬过滤、双路径门控、搜广推要大量自定义；框架变壳，失败模式难讲 |
| ReAct | 「去不去阿拉斯加」不能靠模型 tool 选择；幻觉成本高 |
| 纯端到端 LLM | 假地点、假车程；难评测、产品不可信 |
| 独立向量库 | 语料几十条，内存 cosine + 磁盘缓存足够；上库是过早优化 |
| 开放网页 RAG 作主路径 | 攻略不可规划成逐日行程；质量噪声大 |

**不是框架不好，是问题形状不匹配：** 强约束可验证规划 ≠ 通用文档问答。

## 3. Agent Engineering 经验（简历「难点 / 亮点」）

按「问题 → 做法 → 收益」背，面试官爱听这个。

| # | 坑 / 问题 | 做法 | 收益 |
|---|---|---|---|
| 1 | LLM 编地点 | 闭域 Corpus + POI 兜底；禁止自由生成行程 | 可成行 |
| 2 | 中文对不上英文语料 | `llm_activity_phrase` 先英文化再 embed | 开放词表 |
| 3 | 不像就灌公园 | 语义门控后走 Path B Nominatim | 反骗点击 |
| 4 | RAG 只排序不注入 | `context_blocks` 进 grounded prompt | RAG 真有用 |
| 5 | Chips / NL 两套打分 | chips 合成 query，同一 pipeline | 行为一致 |
| 6 | Prompt 膨胀 | 固定指令 system；user 只带动态事实 | token / 稳定性 |
| 7 | 延迟高 | profile：慢在 LLM；摘要与 OSM **并发**；可切本地 Ollama | 串行 ~96s → warm ~24s |
| 8 | Nominatim 推远处「知名」点 | 大候选池按**距离**重排；活动分地域受限/随处可玩 | 「附近」真近 |
| 9 | 喜欢打爆写库 | 客户端聚合 → `/likes/batch` → TasteSnippet | IO 可控 |
| 10 | 贴纸无限膨胀 | 50+ 活动 → ~10 vibe 图 + LRU | 包体轻 |
| 11 | 无 key 不能演示 | `template` LLM + 关键词 + 目录骨架全链路降级 | 简历可跑 |
| 12 | 群体飞轮 vs 隐私 | 漏斗埋点 → 性格分桶聚合；**k-匿名 + opt-out** | 可讲伦理 |
| 13 | 反馈丢 / 看不见 | 入库 + 低分邮件 + admin 只读；写入 best-effort | 闭环 |
| 14 | 线上难排障 | `trace_id` 端到端 + 500 带栈 + 外部失败统一记账 | 可观测 |

**可背金句：**

> 「相关性永远压不过可行性——车程硬过滤在语义打分之前。」  
> 「RAG 如果不进生成上下文，就只是排序器，不是 Agent 记忆。」  
> 「策略路由用 Python + 语义分，不让 LLM 决定要不要搜 OSM。」

## 4. 个性化与数据飞轮（进阶题）

| 机制 | 注入点 | 说明 |
|---|---|---|
| Persona 测验 / 轴 | 检索打分 + prompt | 单用户偏好 |
| TasteSnippet + likes batch | Surprise / memory RAG | 双击喜欢沉淀口味 |
| User memory 搜/推/广 | score fusion | 当下相关 / 记忆推 / 探索 |
| CrowdSignal（数据层已通） | 待接排序先验 | 性格分桶 × item；k-匿名 |

**讲法：** 单用户向量个性化已落地；跨用户协同是「先合规数据层，再接排序（P3）」——体现产品节奏，不是只会堆模型。

## 5. 可观测 / 工程素养（区别「只会调 API」）

- SearchResponse 带回 `search_path` / `validation` / intent → Agent 决策可调试  
- LLM temperature / token 可配可记  
- Metric 路径**模板化**防基数爆炸；健康检查等噪声 2xx 降采样  
- 客户端也有日志：区分「没到后端」vs「后端挂了」  
- 无完整 pytest 时先写打活体 API 的集成批守回归

## 6. 高频面试问答（Q&A 速查）

**Q：这是 Agent 还是 RAG 应用？**  
A：编排型 Agent：固定流水线里嵌 RAG + 硬约束 + 接地生成 + 校验；不是自治 ReAct Agent，也不是「搜完直接拼 prompt」的薄包装。

**Q：为什么不用 function calling？**  
A：地点与车程是硬正确性约束；tool 选择错误成本高。地理/检索步骤确定性更强，用代码编排，LLM 只做语言与结构化日程。

**Q：幻觉怎么防？**  
A：三道：闭域/POI 定地点 → prompt 限制只用 grounded facts → `validate_grounded_output`，失败回退目录。

**Q：中英文怎么检索？**  
A：不靠巨型同义词表；LLM 把开放说法改成短英文活动短语，再 embedding；失败走关键词降级。

**Q：和 ChatGPT 插件旅行有什么区别？**  
A：我们保证「约束内可出发」：硬过滤 + 可规划语料 + 校验；并有 Surprise/Planner 产品化双入口与个性化闭环，不是单次对话生成。

**Q：规模化怎么演进？**  
A：语料/评价变大再上 pgvector；群体信号进排序；部署 App Runner + Postgres + 托管 LLM；Overpass 缓存与正规 UA；国内再开手机/微信 flag。

**Q：你最大的技术决策是什么？**  
A：把「where」从 LLM 手里拿走，交给可验证检索与规则；LLM 只在接地上下文写「how」。这是正确性与可评测性的根基。

## 7. 简历条目示例（可改写）

- 设计并实现 **Orchestrated RAG Agent**（FastAPI）：闭域检索 → 硬约束过滤 → 双路径 POI 兜底 → Grounded JSON 生成与幻觉校验，支撑 iOS/Web 旅行规划。
