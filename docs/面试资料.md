## 1. 30 秒电梯稿

我做了一个北美「说走就走」旅行规划产品：**iOS（SwiftUI）为主 + Web Beta（React/Vite）同构**，后端 **FastAPI** 跑一套 **编排型 RAG Agent**。

核心不是 Chatbot，而是：**检索与硬约束决定「去哪」，LLM 在接地上下文里写「怎么玩」，校验挡住幻觉**。刻意不用 ReAct / LangGraph——地点幻觉和车程不可靠，不能把「下一步调什么工具」交给模型自选。

## 2. 技术栈全景

### 2.1 一览表（简历可直接摘）

| 层 | 技术 | 面试怎么说 |
|---|---|---|
| **iOS 主产品** | SwiftUI、async/await、URLSession、Keychain JWT | 智能全在服务端；Local/Beta/Custom 可切 API |
| **Web Beta** | React 19、Vite、TypeScript、手写 CSS | 与 iOS 同构双模式；同 Wi‑Fi 外测 |
| **API** | Python 3.10+、FastAPI、Pydantic v2、Uvicorn、httpx | 异步扇出外部 IO；Pydantic 契约 |
| **数据** | SQLAlchemy 2 + SQLite；`.embed_cache.json` | MVP 单机可演示；可换 Postgres |
| **LLM** | OpenAI 兼容 Chat Completions | `.env` 换 Ollama/DashScope/OpenAI 不改编排 |
| **Embedding** | local `bge-small-en-v1.5` 或 API；磁盘缓存 | 无 key 可关键词降级 |
| **RAG** | 自研 `RAGPipeline`（非 LangChain） | 硬过滤 / 双路径 / 搜广推是一等公民 |
| **地理** | Nominatim、Overpass、OSRM、Leaflet | 免 key；best-effort 降级 |
| **可观测** | OTel、Prometheus、`trace_id`、结构化日志 | 串起客户端 → LLM/外部 API |
| **部署** | Docker + nginx compose | Web 同域反代 `/api`；国内 Web+微信 OAuth 就绪 |

### 2.2 产品模型（不是万能聊天页）

| 模式 | 用户意图 | API | 后端 Agent 管线 |
|---|---|---|---|
| **Surprise me** | 今天干嘛 | `/api/activities` → venues | 活动 catalog 向量 + 就近场馆 |
| **Trip planner** | 短途出行 | `/api/plan` 或 `/api/search` → `/api/select` | 闭域 RAG + 接地行程 |

**契约：** 客户端只组装请求、展示、带 JWT；**不做**意图理解 / 检索 / grounding。

### 2.3 前端工程点

**iOS：** `APIClient` Bearer + 120s 超时；Keychain JWT；`.id(language)` 强制刷新；双击 ♥ 本地缓冲 → batch flush；`AssetStore` LRU 贴纸。

**Web：** Vite `host: true` 局域网；薄 `api/client` 与 iOS 行为对齐。

### 2.4 四条硬约束（决定 Agent/LLM 设计）

1. 地点必须真实且可规划  
2. 车程/飞行必须硬过滤（可行性 > 相关性）  
3. 说法开放（中英、新玩法）  
4. 本地可演示、全链路可降级

## 3. 系统架构与分层

```
routers/     → HTTP 契约（plan/search/activities/account/taste/likes/beta…）
agents/      → 业务流程编排（planner / grounded / refiner）
services/    → 可替换能力（RAG / LLM / POI / geo / persona / crowd…）
knowledge/   → 闭域可规划语料 + 贴纸资源
```

**面试话术：** 换 embedding / OSRM / LLM → 动 `services`；换「先检索再接地」流程 → 动 `agents`。

**行程语义三轴（`trip_scope.py`，影响打分）：**

| 轴 | 取值 |
|----|------|
| Drive band | `local` / `regional` / `distant` |
| Travel mode | `drive` \| `fly` |
| `trip_kind` | `local_play` \| `away` |

## 4. AI Agent 专题

### 4.1 我们建的是哪种 Agent？

| 形态 | 采用？ | 说明 |
|------|--------|------|
| **Orchestrated Pipeline Agent** | ✅ | Python 固定编排；LLM 只在定点调用 |
| ReAct / Tool-calling | ❌ | 地点/车程硬正确性；tool 选错成本高 |
| LangGraph / 多智能体 | ❌ | 强约束场景框架收益小 |
| 纯 Chat Agent | ❌ | 要可成行行程，不是闲聊 |
| 薄 RAG（只排序不注入） | ❌ | RAG 必须进 grounded prompt |

**设计灵魂（必背）：**

1. **检索 / 规则定 where** — 可验证、可硬过滤  
2. **LLM 写 how** — 必须 grounded  
3. **`validate_grounded_output`** — 不合格回退目录骨架  

**金句：**

> 「相关性永远压不过可行性——车程硬过滤在语义打分之前。」  
> 「RAG 如果不进生成上下文，就只是排序器。」  
> 「策略路由用 Python + 语义分，不让 LLM 决定要不要搜 OSM。」

### 4.2 Planner 主循环（口述可画）

```
intent / chips
  → understand（规则 + 必要时 LLM 活动短语英文化）
  → rewrite query
  → retrieve（闭域 corpus embedding）
  → hard filter（车程 / specialty / 极光纬度…）
  → score（语义 + 距离轴 + persona + 搜/推/广）
  → 双路径：corpus 命中 | 不够像 → Nominatim POI
  → 并行：weather/OSM/events/social  ‖  summary LLM
  → grounded JSON + validate → 失败回退目录
```

**`/api/plan` vs `/api/search`：** chips 也合成 query 走 **同一 RAG**，避免 RAG 变摆设。`find_candidates` 保证开得动车；RAG 负责像不像。

**延迟：** 摘要 LLM 与 OSM 查询 `asyncio.gather` 并发 — 串行 ~96s → warm ~24s。

### 4.3 RAG Pipeline（`services/rag_pipeline.py`）

**为什么闭域 Corpus：** 命中后一定能生成 day plan（同源 `destinations`）；开放网页只是攻略段落，不可规划。

**步骤：** understand → rewrite → retrieve → hard filter → score → rerank? → **context_blocks 注入生成**

**双路径：**

| 路径 | 条件 | 行为 |
|------|------|------|
| Path A `corpus` | 语义焦点命中目录 | `plan_for_destination` |
| Path B `poi` | focus 但语料不像（如「扔斧头」） | Nominatim → `plan_for_poi` |
| `corpus-approx` | 放宽后弱命中 | 近似选项，避免死胡同 |

语义门控：`_FOCUS_SEMANTIC_MIN=0.55` 等 — 避免「不像就灌国家公园」。

**为什么自研、不用 LangChain / 向量库：** 语料 ~几十条；车程过滤、双路径、搜广推是一等公民写在代码里；Milvus 是过早优化。

### 4.4 Grounded Generation（`agents/grounded.py`）

1. 合并 destination blurb + RAG blocks + OSM 餐饮/玩乐 + 天气  
2. `_GROUNDED_SYSTEM` 放 system；user 只带动态事实  
3. `json_mode` → 逐日 activities JSON  
4. `validate_grounded_output` → hallucination_rate > 40% 回退目录  

**为什么 JSON 不用 Markdown：** 小模型结构崩；前端要稳定字段；解析失败有确定性回退。

### 4.5 Surprise me 轻量 Agent

```
interests/companion/energy → taste 向量 + catalog embed
  → 季节×同伴×体力×预算 打分 + diversify

「附近去哪」→ 地域受限 vs 随处可玩 → 按距离重排（非 importance 推远处大公园）
```

### 4.6 Refiner（`/api/chat`）

规则优先（更近/换目的地/轻松/亲子）→ **0 LLM**；长尾才 RAG + 单次 `generate_summary`。

### 4.7 为什么不用 ReAct / Function Calling？

一次 tool 选错 = 用户白跑。车程、极光纬度、双路径是确定性逻辑，应可测可回归；LLM 做语言与 JSON，不做地理决策。

## 5. LLM 专题

### 5.1 统一入口（`services/llm.py`）

| 函数 | 用途 |
|------|------|
| `generate_summary` | 几乎所有文本/JSON 生成 |
| `analyze_image_json` | 种草 vision 兜底 |
| `parse_itinerary_json` | 抠 JSON |

**没有：** streaming、function calling、多轮 tool loop。

### 5.2 Provider 矩阵

| `LLM_PROVIDER` | 行为 |
|----------------|------|
| `openai` | OpenAI 兼容（OpenAI / DashScope / DeepSeek / Ollama） |
| `anthropic` | Messages API |
| `template` | 不调模型 → 全链路降级 |

只依赖 `chat.completions` 形态；**不硬编内部网关**。

### 5.3 System / User 拆分

固定规则 → **system**（`_SUMMARY_SYSTEM`、`_GROUNDED_SYSTEM`、`_PHRASE_SYSTEM_*`、`_CHAT_SYSTEM`）；动态 facts → **user**。

**收益：** 指令更稳；OpenAI prompt cache 可命中 system 前缀；token 可度量。

### 5.4 Temperature 与 max_tokens

| 场景 | temperature | max_tokens |
|------|-------------|------------|
| json_mode（接地、种草） | 0.2 | 800 |
| 自由 prose（摘要、chat） | 0.7 | 400 |
| 活动短语 | 0.2 | 400 |

### 5.5 调用点与降级

| 调用点 | 目的 | 失败降级 |
|--------|------|---------|
| `resolve_activity_phrase` | 开放词表英文化 | 规则短语 / 关键词 |
| plan summary | 2–3 句 blurb | i18n 模板 |
| `generate_grounded_days` | 逐日 JSON | 目录 day plan |
| refiner | 长尾 chat | 规则 / capabilities 文案 |
| 种草 OCR | 截图结构化 | vision 兜底 |
| discovery 英文化 | Surprise 自由文本 | 仅 taste 向量 |

### 5.6 LLM 闸门 + LRU（省 Token）

1. `rules_cover_activity` → `phrase_from_rules`，**0 token**  
2. 仅 `needs_llm_activity_phrase` 才调 LLM  
3. LRU 512 条 `(query, strict)`；命中记 `cache_hit_count`  

典型：「徒步 3 小时」「观鲸」规则覆盖；重复 query 0 token。

### 5.7 Token 计量与成本

`_record_token_usage()` → OTel span + 日志 `llm tokens prompt=… completion=… cached=…`

**一次完整规划（实测）：** ~1,200–1,500 tokens（短语 ~100 + 摘要 ~300 + grounded ~900–1000）

| 用户强度 | Chat LLM / 天 |
|----------|--------------|
| 轻度 | ~1.3k |
| 中度 | ~3k–4.5k |
| 重度 | ~7k–12k |

### 5.8 种草：OCR 优先，Vision 兜底

`INSPIRATION_EXTRACT_MODE=auto`：RapidOCR 本地提字 → 文本 LLM；失败才 vision（省数千 vision token）。原图不落库。

### 6.1 Embedding

| 配置 | 行为 |
|------|------|
| `EMBEDDING_BACKEND=api` | OpenAI 兼容 embed |
| `local` | `bge-small-en-v1.5` |

| 机制 | 注入点 |

| Persona 六轴 | RAG 打分 + prompt |
| User memory 搜/推/广 | fusion + context_blocks |

## 9. 设计决策一览

| 问题 | 我们怎么做 | 不用 | 为什么 |
|------|-----------|------|--------|
| 地点从哪来 | 闭域 + POI | 纯 LLM 编 | 可验证 |
| 中英新说法 | LLM 英文化 + embed | 同义词表 | 表补不完 |
| 语料不够像 | POI 路径 | 灌公园 | 诚实 |
| RAG 价值 | 注入生成 | 只排序 | 改变内容 |

| 向量存储 | 内存 + 缓存 | 向量库 | 规模小 |
| 生成格式 | JSON + validate | Markdown | 结构稳 |

## 10. 高频面试 Q&A

**Q：Agent 还是 RAG？**  
A：编排型 Agent — RAG + 硬约束 + 接地 + 校验；不是 ReAct，不是薄 RAG。

**Q：为什么不用 function calling？**  
A：地点/车程是硬约束；检索地理用代码编排，LLM 做语言与 JSON。

**Q：幻觉怎么防？**  
A：闭域/POI 定地点 → grounded prompt → validate → 目录回退。

**Q：中英文检索？**  
A：规则优先 + LLM 英文化短语 + embedding；失败关键词降级。

**Q：和 ChatGPT 旅行插件区别？**  
A：约束内可出发 + 双入口产品化 + 个性化闭环；不是单次对话。

**Q：最大技术决策？**  
A：把 where 从 LLM 拿走；LLM 只在 grounded 上下文写 how。

**Q：为什么不用 LangChain？**  
A：车程过滤、双路径、搜广推是一等公民；框架变壳。

**Q：Token 怎么控？**  
A：规则/LRU 闸门；system 前缀稳定；OCR 代替默认 vision。

**Q：规模化？**  
A：pgvector；CrowdSignal 进排序；Postgres；国内 DashScope + 微信 flag。

**Q：为什么 FastAPI 不用 Django？**  
A：非 SSR；异步扇出外部 IO；Pydantic 原生。

**Q：为什么 SQLite？**  
A：MVP 零运维；`DATABASE_URL` 一行升级 Postgres。
