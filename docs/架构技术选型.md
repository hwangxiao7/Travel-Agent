# 架构技术选型说明

> 本文重点回答：**为什么要这么设计**，以及**为什么不用其他常见做法**。  
> 系统怎么跑、API、目录 → [PROJECT_OVERVIEW.md](../PROJECT_OVERVIEW.md)

---

## 0. 先定问题，再选技术

本项目要解决的不是「通用聊天机器人」，而是：

> 用户临时起意（中/英一句话或几个偏好标签）→ 在车程/飞行约束内 → 给出**可执行、可验证**的北美短途行程。

因此设计被四条硬约束钉死：

| 硬约束 | 若不满足会怎样 |
|---|---|
| **地点必须真实且可规划** | LLM 编造「附近冲浪村」→ 用户无法成行 |
| **约束必须硬过滤**（车程/飞行） | 推荐 8 小时外的「完美目的地」→ 产品失败 |
| **说法开放**（中英、新玩法） | 只靠关键词表 → 永远补不完 |
| **本地可演示、可降级** | 绑死云厂商 / 无 key 不能跑 → 简历项目难展示 |

后面所有「用 A 不用 B」都围绕这四条。

## 1. 总体架构：为什么是「编排 Agent + 闭域 RAG」，不是别的

### 1.1 我们选的形态

```
约束/自然语言
  → 检索（定「去哪」，可验证）
  → 硬过滤（车程/飞行）
  → LLM 接地生成（写「怎么玩」）
  → 可选外部增强（天气/餐饮/活动）
```

分层：`agents`（业务流程） / `services`（可替换能力） / `knowledge`（闭域语料）。

### 1.2 备选方案对比

| 方案 | 做法 | 为什么不用 |
|---|---|---|
| **A. 纯 LLM 端到端** | 一句话让模型直接输出行程 JSON | 地点易幻觉；车程不可靠；无法保证「一定能去」；难评测 |
| **B. 纯规则推荐** | if beach → 固定海滩列表 | 无法理解「冲浪/扔斧头/密室」；扩展靠堆 if；无个性化语义 |
| **C. 开放网页 RAG** | 爬博客/Wiki 再生成 | 质量不稳；很多页面不可规划成逐日行程；版权与延迟差 |
| **D. 传统旅游搜索 API 封装** | 只调 Booking/Google Places | 强依赖付费 key；「突发奇想」语义弱；简历项目难讲自研 RAG |
| **E. 本方案：闭域检索 + 接地生成 + POI 兜底** | 目录可规划；新玩法走 OSM | **同时满足可验证、可扩展、可降级** |

### 1.3 为什么要拆 `agents` / `services`

| 做法 | 问题 |
|---|---|
| 全写在一个 `plan()` 大函数 | 换 embedding、换 OSRM、换 LLM 都要改同一坨；难测 |
| 微服务拆成 10 个服务 | MVP / 单人项目运维成本远大于收益 |
| **agents 编排 + services 能力** | 换「怎么 embed」不动「先检索再生成」；面试也好画数据流 |

## 2. 检索设计：为什么是「闭域 Corpus + 语义门控 + POI 双路径」

### 2.1 为什么必须闭域 Corpus（不用开放网页当主检索）

| | 闭域目录 | 开放网页 / 通用向量库 |
|---|---|---|
| 检索命中后 | **一定能**生成 day plan（同源 `destinations`） | 可能只是一篇攻略段落，系统不会「规划」 |
| 质量 | 人工精选亮点与时段 | 噪声大、过时、营销文 |
| 评测 | 金标目的地名可算 P@K | 难定义「正确目的地」 |
| 本项目选择 | ✅ 主路径 | ❌ 不作主检索 |

开放网页适合「问答」；本产品要的是「可出发的行程」，所以主检索必须 ⊆ 可规划集合。

### 2.2 为什么不用「关键词 / 同义词表」做主匹配

早期踩过的坑：中文「冲浪」对不上语料里的 `Surf` → 误判未命中 → 再误用填充词「找个」去搜 POI。

| 方案 | 优点 | 为什么不够 / 不用作主方案 |
|---|---|---|
| 同义词表（冲浪→surf） | 实现简单、零模型 | 说法无穷（「浪点」「paddle out」）；新玩法每次改代码；中英表爆炸 |
| 纯关键词重叠 | 无 embedding 也能跑 | 跨语言几乎必挂；语义近邻（kelp snorkeling vs surfing）分不清 |
| **LLM 改写英文短语 + embedding** | 开放词表；新说法不用改表 | 依赖 LLM/embedding（可用 Ollama；失败则关键词降级） |

**设计意图：** 同义词表是「枚举世界」；改写+向量是「理解世界」。本产品明确要求后者。

### 2.3 为什么要双路径（Corpus vs Nearby POI），而不是「搜不到就随便推公园」

| 方案 | 用户搜「扔斧头」时 | 为什么弃用 / 采用 |
|---|---|---|
| 只返回语料 Top1 | 可能是无关国家公园 | ❌ 体验像骗点击（曾要避免的 park spam） |
| 强制扩写语料覆盖一切玩法 | 目录永远写不完 | ❌ 与「新鲜事物」目标冲突 |
| 空结果报错 | 诚实但产品太硬 | 仅作 POI 也空时的最后手段 |
| **语义不够像 → Nominatim 搜附近真实点** | AxeVentures 等真实场馆 | ✅ 开放玩法有出口，且不污染精品目录 |

**门控用语义分，不用关键词命中：** 避免「中文词不在英文文档里」的假阴性。

### 2.4 为什么 POI 路径仍用 Nominatim 词面搜，而不是再套一层向量库

| 方案 | 为什么现在不用 |
|---|---|
| 自建全量 OSM 向量索引 | 数据量与更新成本对 MVP 过重 |
| Google Places / Foursquare | 要 key、有配额；演示门槛高 |
| Overpass 结构化 tag 主搜 | 更理想的中期方案；但 tag 映射仍要语义层，且 Overpass 易超时 |
| **LLM 短语 + Nominatim** | 零 key、实现快；用改写弥补词面脆弱（并做 query variant） |

诚实限制：Path B 仍是「开放词表的词面检索」，不是语义地点检索。这是**成本与可控性的折中**，不是终局形态（文档末尾写了后续）。

### 2.5 为什么自研 `rag_pipeline`，不用 LangChain / LlamaIndex

| | 自研管线 | LangChain 等 |
|---|---|---|
| 车程硬过滤、极光必须飞、双路径门控、搜广推 | 一等公民，写在 `_metadata_ok` / fusion | 要大量自定义 chain，框架收益变小 |
| 降级路径（无 embed / 无 LLM） | 显式分支，行为可预期 | 抽象层多，失败模式难讲清 |
| 面试讲解 | 一张图说完数据流 | 易变成「调了哪些 Runnable」 |
| 本项目语料规模 | ~几十 doc，不需要框架的 connector 生态 | 大知识库/多数据源时框架更值 |

**不是「框架不好」，是「问题形状不匹配」：** 我们是强约束旅行规划，不是通用文档问答机器人。

### 2.6 为什么不用向量数据库（Milvus / Pinecone / pgvector）

| | 内存列表 + 磁盘缓存 | 独立向量库 |
|---|---|---|
| 语料规模 | 几十条，全量 cosine 可忽略 | 为百万级设计 |
| 运维 | 零 | 多一个进程/云服务 |
| 何时该上 | — | 语料扩到评价/OSM 切片后、或要增量更新时 |

现在上向量库 = **过早优化**，增加演示复杂度，不增加产品正确性。

## 3. 生成设计：为什么是「检索定地点 + LLM 写叙事」，不是「模型搜+写一体」

### 3.1 职责分离

| 步骤 | 谁做 | 为什么 |
|---|---|---|
| 去哪 | RAG / POI（可验证来源） | 地点对错可查、可评测 |
| 怎么排日程 | LLM grounded JSON | 文案与节奏需要语言能力 |
| 校验 | `validate_grounded_output` | 防止模型偷偷加入上下文没有的景点 |

### 3.2 为什么不用「自由生成行程」

自由生成常见失败：不存在的咖啡馆、错误车程、忽略「5.5 小时内」。  
接地生成把模型限制在：语料块 + 附近 OSM + 活动 + 天气。

### 3.3 为什么检索上下文必须注入生成（而不只用于排序）

| 只排序 | 排序 + `context_blocks` 注入 |
|---|---|
| RAG 只影响「选谁」 | 还影响「行程里写什么、偏什么主题」 |
| 用户记忆只改分数 | 记忆片段能进 prompt（喜欢轻松海岸 / 避开陡峭） |
| 面试难说清 RAG 价值 | 能演示「检索改变了生成内容」 |

这是「放大 RAG 价值」的核心设计，而不是调参技巧。

### 3.4 为什么行程要 JSON mode，而不是 Markdown 自由写

小模型（如本地 3B）写 Markdown 常结构崩坏；前端需要稳定的 `time/place/duration/note`。  
JSON + 本地解析失败则**回退精选目录骨架**——再次体现降级，而不是白屏。

## 4. 规划入口：为什么 `/api/plan` 和 `/api/search` 都走 RAG

### 4.1 备选

| 方案 | 问题 |
|---|---|
| chips 只用 haversine + tag 重叠 | 文档写着「个性化 RAG」，主按钮却不走检索 → RAG 变成摆设 |
| 自然语言与 chips 两套打分 | 同一用户两套个性化，行为分裂 |
| **chips 合成 query → 同一 `rag_pipeline` 重排** | 一条管线；RAG 在默认路径也有价值 |

### 4.2 为什么还保留 `find_candidates`

RAG 负责「像不像」；`find_candidates` 先保证「开不开得动车」。  
语义分高但 10 小时车程的目的地，必须被硬过滤掉——**相关性不能压过可行性**。

## 5. 个性化：为什么是「记忆检索 + 搜广推」，不是「只拼一段 profile」

| 方案 | 局限 |
|---|---|
| 把用户简介字符串塞进 prompt | 检索阶段看不到；长历史截断；难做「新颖度」 |
| 只对去过的目的地 ± 分 | 无法泛化到「喜欢海岸」这类主题 |
| **记忆文档向量检索 + 推(相关历史) / 广(新颖) / 搜(当下相关)** | 排序可解释为多目标；生成也能吃到 memory blocks |

UI **故意不展示**原始 搜/广/推 分数：对用户是噪声；对人话「推荐理由」才有产品意义。

## 6. 后端 / 前端技术：为什么选这些，不选常见替代

### 6.1 后端

| 我们用 | 常见替代 | 为什么不选替代 |
|---|---|---|
| **FastAPI** | Django | 非 SSR 站点；要异步扇出外部 IO；Django 偏重 |
| **FastAPI** | Flask | 异步与校验要自己拼；OpenAPI 弱 |
| **FastAPI** | Node NestJS | 团队/生态偏 Python 数据与 LLM；非绝对优劣 |
| **SQLite** | 一上来 Postgres | 演示零运维；`DATABASE_URL` 可升级 |
| **JWT** | Session Cookie 为主 | SPA 跨端口本地开发更简单；可后续加刷新策略 |
| **httpx 异步** | requests 同步 | 天气+OSRM+社媒并行，同步会串行拖死延迟 |
| **Pydantic Settings** | 手写 os.environ | 类型与默认值集中，减少配置漂移 |

### 6.2 前端

| 我们用 | 常见替代 | 为什么不选替代 |
|---|---|---|
| **React SPA + Vite** | Next.js | 无 SEO/SSR 需求；BFF 会与 FastAPI 职责重叠 |
| **Leaflet + OSM** | Mapbox / Google Maps | 免 token；演示与仓库开源友好 |
| **手写 CSS** | Tailwind / MUI | MVP 页面少；减少依赖与设计系统成本 |
| **TypeScript** | 纯 JS | 与后端字段（candidates/explanation）对齐，改 RAG 响应不易漏字段 |

### 6.3 LLM 接入

| 我们用 | 常见替代 | 为什么不选替代 |
|---|---|---|
| **OpenAI 兼容层 + Ollama** | 只绑 OpenAI 云 | 本地免费演示；一套代码两环境 |
| **多 provider（openai/anthropic/template）** | 写死一家 | 降级与切换；CI 可用 template |
| **短模型写 JSON** | 一律上最大模型 | 成本/延迟；本地 3B 需更强约束而非更大模型 |

## 7. 地理栈：为什么是 OSM 全家桶

| 能力 | 我们用 | 不用 | 理由 |
|---|---|---|---|
| 地理编码 / 名搜 | Nominatim | Google Geocoding | 免 key；与 POI 路径一致 |
| 附近餐饮玩乐 | Overpass | Places API | 免 key；结构化；需 UA（已踩坑） |
| 车程 | OSRM | 只 haversine / Mapbox Directions | 真实路网；失败再降级估算 |
| 地图展示 | Leaflet | Mapbox GL | 同免 token 原则 |

**原则：** 主路径尽量「零付费依赖」，付费 API（天气/机票/TikTok）全部 best-effort 增强。

---

## 8. 可观测性：为什么要有，但不上全套 APM

| 我们用 | 不用 | 理由 |
|---|---|---|
| 进程内 OTel spans | 独立 Jaeger 集群 | 单机演示够用；定位「慢在 embed 还是 OSRM」 |
| Prometheus `/metrics` | 只打 console.log | 可聚合延迟/失败；不刷终端 |
| JSON 文件日志 | 终端刷全量 JSON | 开发体验与可检索性平衡 |

## 9. 决策一览（面试可直接背）

| 设计问题 | 我们怎么做 | 明确不用的做法 | 一句话为什么 |
|---|---|---|---|
| 地点从哪来 | 闭域目录 + 必要时 OSM | 纯 LLM 编地点 | 可验证、可成行 |
| 中英 / 新说法 | LLM 英文化 + embedding | 同义词表主匹配 | 开放词表，表补不完 |
| 语料不够像 | POI 路径 | 灌水热门公园 | 诚实 + 仍有结果 |
| RAG 价值如何体现 | 上下文注入生成 | 只排序 | 检索改变行程内容 |
| chips 默认路径 | 合成 query 走同一 RAG | 仅 tag 打分 | 避免 RAG 摆设 |
| 个性化 | 记忆检索 + 搜广推 | 只塞 profile 字符串 | 检索期就个性化 |
| 编排框架 | 自研 pipeline | LangChain 整包 | 强约束场景框架不划算 |
| 向量存储 | 内存 + 磁盘缓存 | 一上来向量库 | 规模不够大 |
| 地图与地理 | OSM 免 key 栈 | 一上来 Mapbox/Google | 演示与降级 |
| 生成格式 | JSON + 校验回退 | 自由 Markdown | 结构稳、可降级 |

## 10. 已知折中与下一步（诚实写清「还不用」的原因）

| 现状折中 | 代价 | 何时改 |
|---|---|---|
| POI 靠 Nominatim 词面 | 短语稍差就空结果 | Overpass tag / 语义地点 API |
| 语料仍偏静态短文 | 新玩法易进 Path B | 评价/OSM/社媒摘要进索引 |
| 本地 embedding 跨语言弱 | 必须 LLM 先英文化 | 换多语 embedding 模型 |
| 评测未全覆盖 POI+接地 | 回归有盲区 | `search_destinations` 端到端金标 |
| RapidAPI 第三方 scraper | 稳定性/ToS 灰；host 易挂 | 已收敛为 dev-only（`ENABLE_SOCIAL_SCRAPING`，默认关）；生产主源走 Reddit/YouTube 官方 API |
| 权威源用公共 Nominatim/Overpass | 政策禁商用批量 | 商用前自建 Nominatim/Overpass 或换付费地编 |

> 合规北极星见 `docs/product-data-compliance-architecture.md`（v1.0）：生产 **不依赖未授权抓取**。`social.enabled_providers` 中 `authorized=True` 的源（Reddit，后续 YouTube）始终可用；scraper 仅在 dev gate 打开时启用。

这些不是「忘了做」，而是 **MVP 边界内的有意取舍**。

## 12. 社媒趋势 ingestion：为什么「提炼成事实」，不是「实时抓来就用」

### 12.1 问题：冷启动没有自有 UGC

自建点评/玩法库需要海量真实用户 → 鸡生蛋。用已有社媒（TikTok / Instagram / 小红书）做冷启动是解法，但**社媒是「发现信号」，不是可再分发的「数据」**。

### 12.2 为什么是后台 ingestion（`agents/ingest.py`），不是每请求实时抓

| 方案 | 问题 / 采用 |
|---|---|
| 每次用户请求现抓 | 每请求都花 API 调用+延迟；成本随用户线性涨；社媒挂了就没数据 |
| **后台按目的地批量抓 → 沉淀 `TrendingSpot`** | ✅ 抓一次多人复用；社媒挂了也有库；成本从「每请求」降到「每目的地每周」 |

管线：多 provider 扇入（`social.enabled_providers`）→ LLM 抽真实地名（中英双名）→ **Nominatim 核实+地编**（真实存在才进库）→ 跨平台去重 + 交叉验证（≥2 平台提到 = 高置信）→ `upsert_spots`。服务端 `planner._social_for` 优先读库，空了才降级实时抓。

### 12.3 为什么只存「事实」，不存原文（法律防火墙）

商用面临授权问题。拆成两个独立风险：**(a) 采集**（违反 ToS）、**(b) 复用**（图文著作权 + 用户隐私/PIPL）。

- 著作权保护「表达」（博主的图/文/账号），不保护「事实」（「有个叫 X 的店在某地」）。
- 因此 `TrendingSpot` **只存**：名字、坐标、类别、出处平台标记、时效戳；**不存**原文、图片、缩略图、作者 handle。
- Nominatim 地编那一步 = 防火墙：社媒说的地方必须在权威源（OSM）真实存在才落库，同时把营销幻觉挡在外。
- 要展示帖子本体 → 用官方 **oEmbed** 现取，不落库。

诚实限制：可再分发的底座应是本就为商用授权而生的源（OSM/ODbL、Google Places/Foursquare/Yelp）；社媒只影响「新鲜度/热度」，不构成侵权主体。
